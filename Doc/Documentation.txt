1. Introduction
1.1 Purpose
This Software Requirements Specification (SRS) defines the complete functional, non-functional, architectural, and implementation requirements for the Distributed Task Scheduler — a real-world mini MapReduce / distributed job execution platform built as a class project.
The purpose of this document is to serve as the authoritative reference for design, development, testing, and deployment of the system. Every engineer or reviewer reading this document should have enough context to implement the system from scratch or evaluate its completeness against industry standards.

1.2 Project Overview
The Distributed Task Scheduler is a backend-heavy, distributed computing system that allows users to submit large jobs that are automatically decomposed into smaller parallel tasks. These tasks are dispatched to multiple independent worker nodes that execute them concurrently, report results, and tolerate failures through automatic retry and reassignment logic.

Real-World Analogy
Think of this system like Google MapReduce, Apache Spark, or Kubernetes Jobs — but simplified for an academic setting. A user submits a 'job' (e.g., process 10,000 records), the system splits it into N tasks, and distributed workers execute them in parallel. The system monitors progress and handles worker crashes gracefully.
1.3 Scope
• Job submission and lifecycle management via a REST API
• Automatic task partitioning from submitted jobs
• Pull-based task distribution to multiple concurrent worker nodes
• Fault tolerance: retry failed tasks, detect stuck tasks, reassign dead worker tasks
• Real-time monitoring dashboard (Vue 3 frontend)
• Worker heartbeat and registration system
• Load balancing through pull-based scheduling

2. System Architecture
2.1 High-Level Architecture Overview
The system follows a Master-Worker distributed architecture. The coordinator (Laravel backend) is the single point of control. Workers are independent, stateless processes that communicate with the coordinator exclusively through the REST API or Redis queues.

SYSTEM ARCHITECTURE DIAGRAM
[Vue 3 Dashboard]  <-->  [Laravel Coordinator API]  <-->  [MySQL Database]
                               |                    
                          [Redis Queue]              
                        /     |      \              
               [Worker 1] [Worker 2] [Worker N]       
2.2 Component Descriptions
2.2.1 Coordinator (Laravel Backend)
The coordinator is the brain of the system. It accepts incoming job requests, partitions them into tasks, manages task state transitions, monitors worker health, and serves the dashboard API.
• Exposes a RESTful HTTP API for clients and workers
• Manages the job and task lifecycle state machine
• Assigns tasks to workers using pull-based scheduling
• Detects and reassigns tasks from dead or timed-out workers
• Pushes real-time events via WebSockets or Server-Sent Events

2.2.2 Worker Nodes
Workers are independent processes — either Laravel artisan commands or standalone scripts — that run in their own terminals, containers, or machines.
• Self-register with the coordinator on startup
• Continuously poll for available tasks (pull-based)
• Atomically claim a single task to prevent race conditions
• Execute task payload logic and report success or failure
• Send periodic heartbeat signals every 10-15 seconds

2.2.3 Database (MySQL)
MySQL provides persistent storage for all entities. Redis complements MySQL for ephemeral, high-speed operations like queuing and heartbeat tracking.

2.2.4 Message Layer (Redis)
Redis serves dual roles: as a Laravel Queue driver for task distribution, and as a pub/sub channel for real-time WebSocket events. Redis also stores worker heartbeat timestamps for fast health checks.

3. Functional Requirements
3.1 Job Management
FR-JOB-01: Submit Job
The system SHALL accept a job submission request containing a name, type, optional description, priority, and an array of task payloads or a dataset to be partitioned.
• Input validation must reject malformed payloads with HTTP 422 and descriptive errors
• On success, return HTTP 201 with the new job object and all created task IDs
• Minimum of 1 task per job; maximum of 10,000 tasks per job

FR-JOB-02: List Jobs
The system SHALL provide an endpoint to list all jobs with filtering by status, pagination (default 20 per page), and sorting by created_at or priority.

FR-JOB-03: Get Job Details
The system SHALL return full job details including all associated tasks, their statuses, assigned workers, and progress percentage computed as (completed_tasks / total_tasks) * 100.

FR-JOB-04: Cancel Job
Users SHALL be able to cancel a job that is in pending or running state. Cancellation marks the job as cancelled and all pending/assigned tasks as cancelled. Running tasks are allowed to finish before the job is marked fully cancelled.

3.2 Task Distribution
FR-TASK-01: Task Partitioning
When a job is submitted, the coordinator SHALL automatically partition it into N tasks. Each task receives a JSON payload slice describing its unit of work. For example, a job to process 1,000 records partitioned into 10 tasks produces tasks each responsible for 100 records.

FR-TASK-02: Atomic Task Claiming (No Race Conditions)
When a worker requests the next available task, the coordinator SHALL use a database-level atomic operation to prevent two workers from claiming the same task. The implementation MUST use one of the following strategies:
• MySQL SELECT ... FOR UPDATE with a transaction (pessimistic lock)
• Atomic Redis LPOP to dequeue task IDs
• Optimistic locking using a version/claimed_at CAS operation

Why This Matters
Without atomic claiming, two workers could read the same 'pending' task simultaneously, both claim it, and execute it twice — causing data corruption or duplicate results. This is one of the most critical correctness requirements in the system.
FR-TASK-03: Pull-Based Scheduling
Workers SHALL pull tasks from the coordinator. The coordinator SHALL NOT push tasks to workers. This ensures natural load balancing: faster workers complete tasks sooner and pull more; slower workers pull fewer. The pull endpoint SHALL return the highest-priority available task for the requesting worker.

FR-TASK-04: Task State Machine
Every task follows a strict state machine. Illegal transitions SHALL be rejected with HTTP 409.
From StateTo StateTriggerActorpendingassignedWorker calls GET /api/tasks/nextCoordinatorassignedrunningWorker calls POST /api/tasks/{id}/startWorkerrunningdoneWorker calls POST /api/tasks/{id}/completeWorkerrunningfailed (retriable)Worker calls POST /api/tasks/{id}/failWorkerrunningpending (timeout)Coordinator detects stuck taskCoordinator (Scheduler)failed (retriable)pendingretry_count < max_retriesCoordinatorfailed (retriable)failed (final)retry_count >= max_retriesCoordinatoranycancelledJob is cancelledCoordinator
3.3 Worker Management
FR-WORKER-01: Worker Self-Registration
A worker SHALL register itself with the coordinator upon startup by calling POST /api/workers/register with its worker_key, hostname, and IP. The coordinator creates a worker record if the key is new, or reactivates an existing record if the worker_key already exists (restart scenario).

FR-WORKER-02: Heartbeat System
Workers SHALL send a heartbeat to POST /api/workers/{key}/heartbeat every 15 seconds. The coordinator records the current timestamp in last_heartbeat_at. Workers that fail to heartbeat within 45 seconds (3 missed intervals) are marked as dead.

FR-WORKER-03: Dead Worker Detection & Task Reassignment
A scheduled Laravel command (runs every 60 seconds via task scheduler) SHALL scan all workers whose last_heartbeat_at is older than 45 seconds. For each dead worker, it SHALL set worker status to dead and reassign all of that worker's running/assigned tasks back to pending status so they can be picked up by a healthy worker.

FR-WORKER-04: Worker Statistics
The coordinator SHALL track and expose per-worker statistics: total tasks completed, total tasks failed, current status, and current task assignment.

3.4 Fault Tolerance & Retry Logic
FR-FAULT-01: Automatic Task Retry
When a task fails (worker reports failure), the coordinator SHALL automatically re-queue it if retry_count < max_retries. The retry_count SHALL be incremented. If retry_count equals max_retries, the task is permanently marked failed.

FR-FAULT-02: Exponential Backoff
Retried tasks SHALL not be immediately available for pickup. A delay SHALL be applied using exponential backoff: delay_seconds = 2^retry_count * 5. For example: first retry = 10 seconds, second retry = 20 seconds, third retry = 40 seconds.

FR-FAULT-03: Task Timeout Detection
A scheduled command running every 2 minutes SHALL check for tasks in running state where the current time exceeds started_at + timeout_seconds. Such tasks SHALL be treated as failures and go through the retry logic. The failure_reason is set to 'task_timeout'.

FR-FAULT-04: Job Failure Propagation
When all tasks of a job have reached a terminal state (done or failed), the coordinator SHALL update the job status. If all tasks are done, the job is completed. If any tasks are permanently failed, the job is failed. Job completion events are broadcast to all connected dashboard clients.

3.5 Dashboard & API
FR-DASH-01: Job Submission UI
The Vue 3 dashboard SHALL provide a form to submit new jobs with fields: name, description, type, priority, and task count (auto-generates test payloads for demo purposes). Form validation must run client-side before API submission.

FR-DASH-02: Jobs List with Live Progress
The dashboard SHALL display a sortable, filterable list of all jobs with: name, status badge, progress bar (%), total/completed/failed task counts, and elapsed time. Data SHALL refresh every 5 seconds via polling or instantly via WebSocket events.

FR-DASH-03: Job Detail Drilldown
Clicking a job SHALL show a detail view with all tasks listed in a table showing task index, status, assigned worker, retry count, duration, and failure reason. Tasks SHALL be color-coded by status.

FR-DASH-04: Worker Status Panel
A workers panel SHALL display all registered workers with their status (idle/busy/dead), last heartbeat timestamp, current task, and cumulative statistics. Dead workers SHALL be visually highlighted in red.

FR-DASH-05: Metrics Panel
A metrics section SHALL display system-wide statistics: total jobs, total tasks, tasks per second (throughput), average task duration, total failures, total retries, and worker utilization percentage.

5. Implementation Guide (Phase-by-Phase)
This section provides step-by-step implementation instructions structured in four phases. Each phase is independently testable before proceeding to the next.

Phase 1: Core Backend Foundation
Phase 1 Goal
By the end of Phase 1, you can submit a job via API and see tasks created in the database. No workers yet.
Step 1.1 — Laravel Project Setup
1. Create new Laravel project: composer create-project laravel/laravel task-scheduler
2. Install dependencies: composer require laravel/sanctum predis/predis
3. Configure .env: set DB_* (MySQL) and REDIS_HOST, QUEUE_CONNECTION=redis
4. Run: php artisan migrate

Step 1.2 — Database Migrations
Create migrations in order (foreign key dependencies require this order):

6. php artisan make:migration create_jobs_table
7. php artisan make:migration create_tasks_table
8. php artisan make:migration create_task_logs_table
Implement each migration using the schema defined in Section 2.3. Run: php artisan migrate

Step 1.3 — Models & Relationships
9. php artisan make:model Worker -m
10. php artisan make:model Job -m
11. php artisan make:model Task -m
12. php artisan make:model TaskLog -m
Add relationships: Job hasMany Tasks. Task belongsTo Job, belongsTo Worker. Worker hasMany Tasks.

Step 1.4 — Job Controller & Partitioning
13. php artisan make:controller Api/JobController --api
Implement store() method: validate input, create Job record, call TaskPartitionerService to split into N tasks, create all Task records in a single DB transaction.

Task Partitioner Service Pattern
Create app/Services/TaskPartitionerService.php. Method: partition(Job $job, int $taskCount): array. This service generates the JSON payload for each task (e.g., {"start_index": 0, "end_index": 99, "job_type": "image_process"}). This is the MapReduce "Map" step.
Phase 2: Worker Nodes & Task Distribution
Phase 2 Goal
By end of Phase 2, you can run multiple workers in separate terminals and watch them pick up and process tasks concurrently.
Step 2.1 — Worker Registration Endpoint
14. php artisan make:controller Api/WorkerController
Implement register() action: use firstOrCreate on worker_key. Set status to idle and update last_heartbeat_at on re-registration.

Step 2.2 — Task Claiming with Atomic Lock
This is the most critical piece of code. The task claiming MUST be atomic to prevent race conditions.
// TaskController@next — Atomic task claiming
public function next(Request $request): JsonResponse {
    $worker = Worker::where('worker_key', $request->header('X-Worker-Key'))->firstOrFail();
    $task = DB::transaction(function () use ($worker) {
        $task = Task::where('status', 'pending')
            ->orderBy('created_at')->lockForUpdate()->first();
        if (!$task) return null;
        $task->update(['status'=>'assigned', 'worker_id'=>$worker->id, 'assigned_at'=>now()]);
        return $task;
    });
    if (!$task) return response()->json(['message'=>'no_tasks_available'], 204);
    return response()->json($task);
}
Step 2.3 — Worker Artisan Command
15. php artisan make:command WorkerRun
Implement the worker loop inside the handle() method. The worker runs in an infinite loop: poll for task, execute, report result, send heartbeat. See the worker loop pseudocode:
• Register with coordinator (POST /api/workers/register)
• Loop forever: GET /api/tasks/next
• If no task: sleep(3), continue
• POST /api/tasks/{id}/start
• Execute payload (simulate with usleep, or implement real logic)
• POST /api/tasks/{id}/complete or /fail
• Heartbeat is sent every 15 seconds regardless of task state

Step 2.4 — Running Multiple Workers
Open three separate terminal windows and run:
• Terminal 1: php artisan worker:run --key=worker-001
• Terminal 2: php artisan worker:run --key=worker-002
• Terminal 3: php artisan worker:run --key=worker-003

Phase 3: Fault Tolerance & Reliability
Phase 3 Goal
By end of Phase 3, killing a worker mid-task will result in the task being automatically reassigned to a healthy worker within 60 seconds.
Step 3.1 — Heartbeat Endpoint & Dead Worker Detection
16. Add heartbeat route: POST /api/workers/{key}/heartbeat
17. php artisan make:command DetectDeadWorkers
The command logic: find all workers where last_heartbeat_at < now() - 45 seconds AND status != dead. For each: set status = dead, find all their assigned/running tasks, set those tasks back to pending, increment retry_count.
18. Register in app/Console/Kernel.php: $schedule->command('workers:detect-dead')->everyMinute()

Step 3.2 — Task Timeout Detection
19. php artisan make:command DetectTimedOutTasks
Logic: find tasks where status = running AND started_at < now() - timeout_seconds. Apply same fail/retry logic as dead worker detection. Schedule to run every 2 minutes.

Step 3.3 — Retry with Exponential Backoff
When re-queuing a retried task, set a available_after timestamp = now() + (2^retry_count * 5) seconds. Modify the task claim query to include AND (available_after IS NULL OR available_after <= NOW()).

Step 3.4 — Job Status Propagation
After every task state change, call a JobStatusService::recalculate(Job $job) method. This method counts done/failed/pending tasks and updates the job status accordingly.

Phase 4: Vue 3 Dashboard
Phase 4 Goal
A real-time Vue 3 dashboard that shows all jobs, task progress, worker statuses, and system metrics — updating live.

Create src/services/api.js using Axios with baseURL pointed at the Laravel API. Export functions: getJobs(), getJob(id), submitJob(data), getWorkers(), getMetrics(). Use Pinia stores to cache and reactively update this data.

Step 4.3 — Dashboard Components
Build these Vue components in src/components/:
• JobsTable.vue — sortable job list with status badges and progress bars
• JobDetail.vue — drilldown task table with color-coded statuses
• WorkersGrid.vue — card grid showing each worker's status, heartbeat, and stats
• MetricsBar.vue — top-level KPI row (total jobs, throughput, worker count)

Step 4.4 — Polling / Real-Time Updates
For polling (simpler): in each component's mounted() hook, set an interval to call the API every 5 seconds. Clear the interval in unmounted(). For WebSockets (impressive): install laravel-echo and pusher-js, configure Laravel Broadcasting with Pusher or Soketi (self-hosted).


6. Non-Functional Requirements
6.1 Performance
• The coordinator API SHALL respond to task claim requests within 200ms under normal load
• The system SHALL support at least 10 concurrent worker nodes
• Task throughput SHALL reach at least 50 tasks/minute with 5 active workers
• Database queries on tasks table SHALL use indexes on (status, job_id, worker_id)

6.2 Reliability
• No task SHALL be permanently lost due to a worker crash (guaranteed by dead worker detection)
• No two workers SHALL execute the same task simultaneously (guaranteed by atomic claiming)
• The scheduler commands SHALL run reliably without missed executions

6.3 Scalability
• Adding more workers SHALL linearly increase throughput without coordinator changes
• The database schema SHALL support up to 1 million tasks without index degradation

6.4 Security (Basic)
• Worker API endpoints SHALL require the X-Worker-Key header
• SQL injection is prevented by using Laravel Eloquent parameterized queries
• CORS is configured to allow only the Vue frontend origin

6.5 Maintainability
• All business logic SHALL be in Service classes, not controllers
• All scheduled commands SHALL log their actions to storage/logs/scheduler.log
• PHPUnit tests SHALL cover: task claiming atomicity, retry logic, dead worker detection

8.2 Integration Tests
• Submit a job with 50 tasks, start 3 workers, verify all tasks complete
• Kill a worker mid-execution, verify tasks are reassigned within 60 seconds
• Simulate task failure, verify retry and eventual failure after max_retries

8.3 Manual Test Scenarios

25. Network Failure: Block worker heartbeat ? worker marked dead ? tasks redistributed
26. Task Failure: Worker reports failure ? retry 3 times ? permanent failure
27. Load Test: Submit 1,000-task job with 5 workers ? measure throughput

10. Evaluation Criteria & Grading Guide
This section maps each core requirement to implementation evidence so you can verify your implementation is complete and impressive.

RequirementImplementation EvidencePoints WeightJob Queuejobs + tasks tables; POST /api/jobs creates job + N tasks atomically15%Worker Nodes3+ workers running concurrently via artisan command; all registered in workers table20%Retry Failed Tasksretry_count incremented on failure; task re-queued until max_retries; exponential backoff20%Load BalancingPull-based model demonstrated: faster workers claim more tasks; no push mechanism15%Race Condition PreventionlockForUpdate() transaction visible in code; no duplicate task execution in logs10%Dead Worker DetectionKill a worker, wait 60s, verify tasks reassigned in task_logs10%Vue DashboardLive progress bars, worker status panel, job submission form10%Extra Credit: Dockerdocker-compose.yml with 3+ worker containers, coordinator, mysql, redis+5%Extra Credit: WebSocketsReal-time updates via Laravel Echo + Soketi/Pusher+5%
Critical Success Factors
1. Atomic task claiming — if you can demonstrate that 10 concurrent workers never get the same task, you have proven the core distributed systems concept. 2. Dead worker reassignment — demonstrate this live: kill a worker, show the task is picked up by another worker. 3. Multiple real workers — running 3+ independent worker processes (or containers) is what makes this a distributed system.
